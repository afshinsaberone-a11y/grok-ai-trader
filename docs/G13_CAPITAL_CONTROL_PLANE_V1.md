# G13 Capital Control Plane v1

## Purpose and boundary

`tools/forexai_control_plane_v1.py` is the upstream producer for the G13 controlled-Demo path. It consumes a fresh one-shot signal intent from a generated EURUSD M15 candidate, validates the exact successful Promotion bundle and the three successful upstream evidence runs against the current `main` SHA, observes the actual MT5 account and current market quote, performs a read-only broker `order_check`, calculates account-currency stop-loss exposure through `MetaTrader5.order_calc_profit`, and then uses the repository's `TradeLedger`, `CapitalFirewall`, authenticated runtime envelope, and MQL5 authorization record.

The Control Plane never calls `order_send`, never changes the kill switch to `ALLOW`, and never authorizes a real account. Before any Ledger mutation, envelope, or `.auth` publication, it also requires a fresh one-signal admission request signed by the independent Ed25519 provider and verifies the request against the current intent, candidate configuration, Promotion SHA/run, Validation/Robustness/OOS source run IDs, promoted candidate set, and risk budget. This signed grant must explicitly state `demo_trading_allowed=true` and `live_trading_allowed=false`; the Promotion manifest itself continues to state `demo_trading_allowed=false` because Promotion approves research/package generation, not trading permission. A local `ALLOW` switch is necessary for the EA but never substitutes for the signed grant.

The producer consumes the exact verified admission file immediately before the first Ledger append, making it one-shot and freeing the configured provider output path for the next request. A failure after that point is not retried automatically; reconcile the append-only Ledger and provider issuance registry before requesting any new grant. The generated EA independently checks Demo account status, quote drift, actual risk, record bindings/integrity, decision ID, age, the kill switch and an atomic single-attempt lock before its one order attempt. The authorization record has a 10-second maximum age. If the outcome of an order attempt is unknown, the EA does not retry.

## Prerequisites for a controlled Demo window

1. Merge and validate the PR first. G13 Validation/Robustness/OOS/Promotion/Compile-Parity/readiness workflows must succeed for the same current `main` SHA. The service refuses a stale Promotion artifact.
2. Configure the protected HMAC and Demo identity secrets `FOREXAI_CONTROL_PLANE_HMAC_SECRET`, `FOREXAI_EXPECTED_DEMO_ACCOUNT_LOGIN`, and `FOREXAI_EXPECTED_DEMO_ACCOUNT_SERVER`. Use only the real trusted values. Do not paste any secret value into chat, issue comments, logs, or source control. Missing or mismatched account identity blocks authorization. Do not use made-up credentials just to turn the gate green.
3. Configure repository Variables `FOREXAI_CONTROL_PLANE_ADMISSION_PUBLIC_KEY` (base64 encoding of the independent provider's 32-byte Ed25519 public key) and `FOREXAI_CONTROL_PLANE_ADMISSION_REQUEST_PATH` (the absolute path for the one-signal request on the MT5 runner). The parent directory must already exist with ACLs that allow the independent provider to create the request and the runner service to read/delete it, while preventing untrusted writers. The request file itself does **not** need to exist when the workflow starts: the workflow validates the directory and the provider publishes a new signed file only after receiving the corresponding fresh EA intent. The Ed25519 private key and signing process must stay outside this repository and the MT5 runner. Each request is accepted for at most 30 seconds. A stale, unsigned, replayed, wrong-candidate, wrong-trade, wrong-config or policy-conflicting request must fail closed before new Ledger events or authorization artifacts are published. If a failed or expired request remains at the configured path, reconcile it with the provider's issuance registry and remove it safely before asking the provider to issue another grant; its issuer intentionally refuses to overwrite existing output. Never generate or re-sign admission requests on the execution runner just to pass the gate.
4. Confirm the interactive MT5 terminal is connected to the intended **Demo** account and the `EURUSD` M15 generated EA is attached to its chart. In the EA inputs, explicitly set `DemoTradingAuthorized=true` for the chosen candidate. The source default remains `false`.
5. Run **Actions → ForexAI Capital Control Plane v1 → Run workflow** and explicitly select the one candidate ID for this Demo window (default `2`). Signals from other promoted candidates cannot receive authorization. The workflow deliberately writes `DENY` first, validates the selected ID against the current Promotion manifest, and verifies the exact Promotion artifact digest.
6. The independent provider must issue a signed request tied to the exact fresh intent and current evidence. The Control Plane cross-checks the grant and the local signal before appending any Ledger event. A grant that does not pass those checks will result in `BLOCKED`; do not attempt to bypass the rejection.
7. Only after the signed admission has been verified, account and candidate identities have been independently confirmed, and the controlled Demo policy has been explicitly approved, an operator may change `g13_demo_kill_switch.txt` to `ALLOW` in the resolved MT5 Common Files directory for the controlled Demo window. Neither the service nor its cleanup step performs this change. If anything is uncertain, keep `DENY`.
8. The producer verifies the persisted hash-chained Ledger, the signed envelope's current Capital Firewall authority, and the just-written MQL5 authorization record by reading the files back before it exposes the one-shot token. Do not dispatch the separate `ForexAI Capital Firewall Authorization Preflight` while this service is occupying the only self-hosted MT5 runner. After the service exits, its cleanup deliberately deletes temporary authorization/intent files and leaves `DENY`; a later read-only preflight should not be expected to find a fresh token.
9. Cancel the long-running Control Plane workflow to end the window. Its `always()` cleanup writes `DENY` and removes any remaining G13 `.auth`, pending-intent, and configured admission-request files. The provider issuance registry may already have reserved a grant if a post-consumption failure occurred; reconcile before retrying. Verify the final `DENY` result in the workflow summary.

## Local files and secrets

The service uses the Windows `ProgramData` directory under `ForexAI\\ControlPlane` for its hash-chained `trade-ledger.jsonl`, latest `authenticated-envelope.json`, and the exact Promotion evidence bundle. That directory is restricted to SYSTEM and Administrators by the workflow. The Promotion files contain public/provenance evidence, not HMAC keys. The HMAC key is injected only from the GitHub Actions secret into the service process.

The MT5 terminal profile/Common Files path is resolved from the running terminal owner with `tools/resolve_mt5_common_files_v1.ps1`; paths and actual account identity are kept out of public logs. Authorization is pinned to both the protected expected Demo login and exact server name. The service fails closed if the terminal cannot be resolved, if a required file/secret is missing, if the account is not the configured Demo account, if quotes are stale, if candidate/manifest/provenance hashes do not match, if the broker rejects `order_check`, if another G13 position/pending order exists, if risk exceeds the frozen Promotion cap, or if the kill switch is not already `ALLOW`.

## Ledger lifecycle and recovery

For each fresh signal bar the producer derives a deterministic trade identity from candidate ID and the signal-bar epoch; operators do not supply or guess a Trade ID. Under a single-writer lock it appends `PROPOSED → VALIDATED → RISK_RESERVED`, issues the risk authorization, moves to `AUTHORIZED`, reserves the amount, authenticates the runtime envelope, and atomically publishes the envelope and the one-shot `.auth` record.

If an error happens during publication, the producer does not try to manufacture missing evidence or submit an order. The durable ledger is authoritative; inspect the redacted preflight, private machine files and G13 runtime evidence before recovering. Do not manually edit the append-only ledger or hand-write `.auth` files.

## Explicit exclusions

- No local or self-signed substitute for the independent Ed25519 admission provider.
- No live-account authorization or Live enablement.
- No synthetic prices, fabricated broker snapshots, guessed Trade IDs, test-created credentials, fake envelope, fake Ledger event or hand-written authorization record in production.
- No `order_send` call in the Control Plane.
- No automation that changes `DENY` to `ALLOW`.
- No automatic retries when an order result is ambiguous.
